# 失败结束 `flow.fail`

失败节点在工作流已经确认无法继续时提交失败终态。`error_expression` 生成最终错误文本，可以引用输入和已保存结果。它适合业务规则拒绝、补偿失败或明确不可恢复的状态。暂时性网络错误和可以重试的任务错误应留在任务节点处理，不要过早把运行关闭。

## 错误内容

错误信息要给操作者足够的业务上下文，例如失败阶段、外部引用和可执行的下一步。令牌、凭据、完整请求头、敏感输入与未脱敏的外部响应不能写入错误文本。需要保留诊断细节时，可在受控遥测系统中记录关联 ID，并让终态只保存安全摘要。

`error` 数据端口可以从上游传入字符串，表达式也可以从字段组合文本。最终内容必须稳定可重放，不能加入新的当前时间、随机 ID 或实时远程状态。失败节点没有出站端口。需要走人工修复或降级分支时，应在进入本节点前完成判断和补偿，确认运行确实不能继续后再提交终态。

## 运行与告警

测试应覆盖缺失错误字段、敏感内容脱敏、重复终态提交、取消期间清理失败以及任务重试耗尽产生的失败。监控可以分别统计显式失败节点与任务直接失败，前者通常表达业务判断，后者更接近执行问题。告警规则应使用稳定错误码或关联字段，避免依赖经常变化的整段自然语言。
