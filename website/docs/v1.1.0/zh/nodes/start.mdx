# 开始 `flow.start`

开始节点定义一张顶层图怎样被识别和启动。每个可执行工作流只保留一个开始节点，并且不接收入站控制边。`next` 把控制交给第一个业务节点，`input` 则把已经通过输入结构检查的启动数据提供给后续表达式。容器内部使用各自的内部入口，不再放置开始节点。

## 身份与运行入口

`workflow_name` 是长期稳定的业务身份，`workflow_version` 用于区分不兼容的定义。`runtime_kind`、`entrypoint` 和 `export_name` 共同告诉宿主到哪里加载工作流函数。发布前应确认入口真实存在，导出名称与构建产物一致，并且负责该版本的 worker 已经上线。已有运行依赖旧入口时，需要保留兼容构建与路由，不能直接覆盖后再移除旧代码。

`input_schema` 只声明工作流确实读取的字段。宽松结构便于试验，但生产发布应明确必填项、数据类型和嵌套对象，避免错误输入走到持久步骤以后才失败。`run_id_expression` 可以从订单号、任务号等稳定输入生成运行 ID。表达式为空时由宿主分配身份，有值时重复启动请求可以命中同一个运行。

## 接线与发布检查

开始节点通常先连接条件、任务或容器。数据边应从 `input` 接到接受兼容 JSON 值的端口，控制边从 `next` 接到目标的 `in`。画布标题和位置可以随编辑调整，节点 ID、工作流名称和版本在创建运行后应保持稳定。发布检查还要覆盖输入样例、重复启动、缺失入口、旧 worker 路由和第一条控制边，确认图不会从未连接的入口停住。
