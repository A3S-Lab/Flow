# 超时结束 `flow.timeout`

超时节点提交独立的超时终态，并保存触发该结论的 UTC 截止时间。它适合 SLA、审批窗口、支付期限和其他到期后不能继续的业务边界。节点本身不会等待时钟，也不会定期检查当前时间。通常先由等待节点持久化同一个截止时间，唤醒后再进入本节点。

## 截止时间与原因

`deadline` 是必填日期时间表达式，结果应带时区并且来自稳定输入或已保存结果。`reason` 是可选的简短业务说明，用来区分哪一个窗口到期。截止时间参与运行结论，不能在重放时重新读取当前时钟生成。需要相对时长时，先在开始或任务结果中固定基准时间，再计算并保存绝对时间。

节点接收 `in`，并可以从 `deadline` 数据端口取得时间，提交后没有出站控制。多个截止窗口存在时，可以使用不同等待和超时节点，让每个节点 ID 对应清楚的业务边界。若到期后仍允许补偿、通知或人工复核，应在提交超时终态前完成这些步骤，或把后续工作交给独立子工作流。

## 调度与观测

测试要覆盖时区偏移、已经到期、调度延迟、重复唤醒、进程恢复和取消竞争。监控应分别记录业务截止时间、实际唤醒时间与终态提交时间，方便判断延迟来自业务配置、调度器还是 worker 容量。错误信息和 reason 不要包含凭据或完整外部响应，详细诊断使用受控关联 ID。
