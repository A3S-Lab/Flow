# 取消运行 `flow.cancel`

取消节点结束一个已经收到持久取消请求的运行。它没有配置字段，也不能当作普通条件分支的出口。宿主先把取消请求和原因写入历史，工作流随后可以释放锁、撤回外部任务、通知子运行或执行补偿，最后进入本节点提交取消终态。

## 清理顺序

取消请求到达后，运行代码仍可能需要若干持久步骤完成清理。每项清理使用独立且稳定的节点身份，并且能够处理重复交付。外部资源释放失败时，应选择重试、记录失败或转人工处理，不能直接跳过关键清理。受管子工作流仍在执行取消流程时，父运行需要等待其解析。

节点只接收 `in` 控制端口，没有数据和出站端口。取消原因沿用原请求，图中不另行配置。缺少持久取消请求时，引擎会拒绝提交这个终态，因此普通业务上的撤单、拒绝或关闭需要先明确它们是否属于工作流取消。若它们只是业务结果，可以使用条件分支加完成或失败节点表达。

## 竞争与验证

测试应覆盖任务完成与取消同时到达、Hook 接收与取消竞争、子工作流取消、清理步骤重试、重复取消请求和进程重启。最终历史只能出现一个终态。控制面应向调用者返回已经接受、正在清理或已经取消的真实状态，并保留原始取消原因与请求身份，方便操作者判断清理进度。
