# Child workflows

First-class child workflows preserve parent-child authority across crashes that occur between two event streams.

## Start one child

```rust
Ok(ctx.start_child_workflow(
    "invoice",
    invoice_spec,
    serde_json::json!({ "order_id": order_id }),
))
```

The child ID is stable within the parent history. Replaying the same command adopts the existing child instead of creating another run.

## Start a bounded batch

```rust
let children = items
    .into_iter()
    .enumerate()
    .map(|(index, item)| {
        ctx.child_workflow(
            format!("item-{index:04}"),
            child_spec.clone(),
            serde_json::json!({ "item": item }),
        )
    })
    .collect();

Ok(ctx.start_child_workflows(children))
```

Flow validates the complete batch and persists every generated child identity before execution begins. A batch contains at most `MAX_CHILD_WORKFLOW_BATCH_SIZE` children, currently 64.

Split larger fan-outs into stable windows. Emit the next window only after all outcomes in the current window are durable.

## Ordering

Siblings may execute concurrently. The parent records terminal outcomes in request order rather than completion order so replay cannot depend on scheduler timing.

## Cancellation policy

The default policy propagates a parent cancellation request to an open child and waits for its terminal result. Use `start_child_workflow_with_policy` or `child_workflow_with_policy` when the relationship requires another documented policy.

## Recovery windows

Flow handles both crash directions:

- the parent records child intent before child creation;
- the child exists before the parent records adoption;
- the child finishes before the parent records its outcome.

Recovery reconciles the stable identities instead of rerunning completed child work.
