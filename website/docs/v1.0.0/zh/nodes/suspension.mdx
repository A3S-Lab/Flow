# 等待与外部输入节点

这三类节点都会让运行暂停并释放 worker。事件存储保留等待条件，调度器或外部调用在条件满足后写入事件，再由任意兼容 worker 继续重放。

## 定时等待 `WaitUntil`

定时等待保存一个稳定身份和绝对 UTC 时间。它适合业务截止时间、延迟重试以外的冷却窗口、轮询间隔和定时释放。

| 属性        | 类型            | 必填 | 规则                                 |
| ----------- | --------------- | ---- | ------------------------------------ |
| `wait_id`   | `String`        | 是   | 运行内稳定身份，同一逻辑等待始终复用 |
| `resume_at` | `DateTime<Utc>` | 是   | 绝对 UTC 时间，第一次创建后不可改变  |

```rust
let wait_id = "payment-window";
let resume_at = ctx
    .input()["payment_deadline"]
    .as_str()
    .ok_or_else(|| FlowError::Runtime("missing payment_deadline".into()))?
    .parse::<DateTime<Utc>>()?;

if !ctx.wait_completed(wait_id) {
    return Ok(ctx.wait_until(wait_id, resume_at));
}
```

首次返回命令会写入 `WaitCreated` 并暂停。时间到了以后，宿主可以调用 `resume_wait()`，使用 `FlowScheduler` 扫描到期项，或通过任务队列派发定向恢复。创建一个截止时间已经过去的等待也会先形成持久记录，仍需恢复路径提交完成事件。

后续重放用同一 `wait_id` 返回不同 `resume_at` 会得到 `NonDeterministic`。等待完成后再次返回同一命令会继续重放，工作流应通过 `wait_completed()` 进入下一阶段。

清理式取消会把已有等待标记为取消。清理路径需要等待时，使用新的稳定 ID，例如 `cleanup-backoff-1`。继续返回已经取消的 ID 会被拒绝。

## 命名信号 `WaitForSignal`

信号适合同一名字可能收到多条消息的业务输入，例如库存变化、人工意见或设备状态。信号先进入历史，再按接收顺序与等待配对。

### 工作流定义

信号名称必须在创建运行前写入 `WorkflowSpec`。

```rust
let spec = WorkflowSpec::rust_embedded(
    "order.approval",
    "1.0.0",
    "workflows::order",
    "main",
)
.with_signal("order.approved")
.with_signal("order.rejected");
```

没有声明的名称无法投递，也不能建立等待。声明集合属于不可变运行定义，不能在运行中追加。

### 等待属性

| 属性          | 类型     | 必填 | 规则                               |
| ------------- | -------- | ---- | ---------------------------------- |
| `wait_id`     | `String` | 是   | 非空，每次消费使用独立稳定身份     |
| `signal_name` | `String` | 是   | 非空，并且已在 `WorkflowSpec` 声明 |

```rust
if let Some(payload) = ctx.signal_payload("approval-1") {
    return Ok(ctx.complete(payload.clone()));
}

Ok(ctx.wait_for_signal("approval-1", "order.approved"))
```

一个等待只消费一条消息。同名等待按创建事件序号排序，同名信号按接收事件序号排序，最早等待配最早未消费消息。需要连续读取三条消息时，应使用 `approval-1`、`approval-2` 和 `approval-3` 等确定性 ID。

### 投递属性

外部调用通过 `FlowEngine::send_signal()` 发送 `WorkflowSignal`。

| 属性        | 类型     | 必填 | 规则                                 |
| ----------- | -------- | ---- | ------------------------------------ |
| `signal_id` | `String` | 是   | 调用方拥有的幂等身份，重试时原样复用 |
| `name`      | `String` | 是   | 已声明的信号契约名称                 |
| `payload`   | JSON     | 是   | 完整业务载荷，进入持久历史           |

```rust
let signal = WorkflowSignal::new(
    "approval-delivery-8421",
    "order.approved",
    json!({ "approved_by": "manager-17" }),
);

let snapshot = engine.send_signal(&run_id, signal).await?;
```

相同运行 ID 与 `signal_id` 的重投必须保持名称和载荷一致。值发生变化会返回 `SignalConflict`。投递到续段链的根 ID 时，引擎会找到活动叶子，同时在整条链中检查先前是否已经收到该 `signal_id`。

运行终止后不能接收新信号。已经持久化但尚未消费的信号也会阻止 `continue_as_new()`，避免消息在段边界丢失。

## 外部 Hook `CreateHook`

Hook 适合一次外部请求需要公开令牌、审计元数据以及接收或撤回状态的场景。审批链接、Webhook 回调和一次性人工输入通常使用 Hook。

| 属性       | 类型     | 必填 | 规则                                           |
| ---------- | -------- | ---- | ---------------------------------------------- |
| `hook_id`  | `String` | 是   | 运行内稳定身份                                 |
| `token`    | `String` | 是   | 外部路由使用的 bearer 值，活动 Hook 中保持唯一 |
| `metadata` | JSON     | 否   | 审计与宿主路由信息，默认空 JSON 值             |

```rust
let hook_id = "manager-approval";

if let Some(payload) = ctx.hook_payload(hook_id) {
    return Ok(ctx.complete(payload.clone()));
}
if ctx.hook_disposed(hook_id) {
    return Ok(ctx.fail("approval was withdrawn"));
}

let metadata = HookMetadata::human_approval("Approve order ord-1042")
    .with_callback_route(HookCallbackRoute::post("/callbacks/flow/hooks"))
    .with_label("tenant", "acme")
    .with_data("order_id", json!("ord-1042"));

Ok(ctx.create_hook_with_metadata(
    hook_id,
    "opaque-public-token",
    metadata,
)?)
```

`HookMetadata` 提供一组可选的标准字段。

| 字段              | 类型             | 用途                     |
| ----------------- | ---------------- | ------------------------ |
| `kind`            | `String`         | 应用定义的路由与审计分类 |
| `subject`         | `Option<String>` | 人类可读主题             |
| `callback.method` | `String`         | 大写 HTTP 方法           |
| `callback.path`   | `String`         | 宿主拥有的公开路径       |
| `labels`          | 字符串映射       | 可检索的低体积标签       |
| `data`            | JSON 映射        | 应用结构化元数据         |

这些字段只进入历史，不会自动创建 HTTP 路由。宿主负责认证回调请求、从令牌找到活动 Hook，并限制载荷大小。

### 接收与撤回

| API                                     | 适用方式               | 重投规则            |
| --------------------------------------- | ---------------------- | ------------------- |
| `resume_hook(run_id, hook_id, payload)` | 调用方已经保存稳定身份 | 同值接收可可靠重投  |
| `resume_hook_by_token(token, payload)`  | 第一次只知道公开令牌   | 只查询当前活动 Hook |
| `dispose_hook(run_id, hook_id)`         | 以稳定身份撤回         | 同一撤回可可靠重投  |
| `dispose_hook_by_token(token)`          | 第一次按公开令牌撤回   | 只查询当前活动 Hook |

第一次按令牌解析成功后，应保存返回的运行 ID 和 Hook ID。Hook 已经接收或撤回以后，活动令牌索引不再返回它，稳定身份接口仍能判断重投是否与历史一致。

同一个 Hook 不能同时接收和撤回。接收载荷发生变化、令牌改变或元数据改变都会产生明确冲突。错误的 `Display` 与 `Debug` 会遮蔽令牌值，业务日志也不应自行打印它。

取消请求会关闭当前活动 Hook。清理阶段需要新的外部确认时，使用新的 Hook ID 和令牌。

## 信号与 Hook 的选择

| 情况                          | 选择     |
| ----------------------------- | -------- |
| 同一名称会收到多条排队消息    | 信号     |
| 一条消息需要调用方自有幂等 ID | 信号     |
| 一次请求需要公开 bearer 令牌  | Hook     |
| 需要明确的接收与撤回状态      | Hook     |
| 只需等到固定时刻              | 定时等待 |

三类节点都不会占用一个睡眠中的 worker。生产部署要同时配置恢复扫描、定向任务派发和活动 Hook 索引，单有事件存储无法让暂停项自动继续。
