# 子工作流、续段与容器

这一组能力处理两件相邻的事。运行命令可以把工作拆到子工作流或新的历史段中，图容器则给画布建立独立作用域。子工作流和续段由引擎直接执行。`iteration` 与 `loop` 只参加图结构校验，容器里的业务规则仍由宿主提供。

## 单个子工作流 `StartChildWorkflow`

单个子工作流适合一项有独立输入、历史和终态的工作。父运行持久保存请求，引擎分配全局子运行 ID，随后启动或恢复该子运行。子运行到达终态后，父历史会追加 `ChildWorkflowResolved`，工作流代码在下一次重放中读取结果。

| 属性                  | 类型           | 必填 | 规则                                            |
| --------------------- | -------------- | ---- | ----------------------------------------------- |
| `child_id`            | `String`       | 是   | 父运行内稳定且非空，重放时保持不变              |
| `spec`                | `WorkflowSpec` | 是   | 完整而且可校验的子工作流定义                    |
| `input`               | JSON           | 是   | 子运行的初始输入，按值写入父历史                |
| `cancellation_policy` | 枚举           | 否   | 默认 `request_cancellation`，也可设为 `abandon` |

`WorkflowSpec` 会固定子运行使用的定义与运行时。

| `spec` 属性           | 类型                           | 规则                             |
| --------------------- | ------------------------------ | -------------------------------- |
| `name`                | `String`                       | 稳定的工作流类型名称，不能为空   |
| `version`             | `String`                       | 应用定义版本，不能为空           |
| `runtime.kind`        | `native_ts` 或 `rust_embedded` | 决定由哪个运行时家族重放         |
| `runtime.entrypoint`  | `String`                       | 运行时入口，不能为空             |
| `runtime.export_name` | `String`                       | 导出函数，不能为空               |
| `runtime_build_id`    | 可选构建身份                   | 把新运行固定到可重放它的部署构建 |
| `patch_markers`       | 标记集合                       | 在创建时一次写入，续段也会继承   |
| `signal_names`        | 名称集合                       | 子工作流接受的信号契约           |

下面的工作流先读取已经持久化的结果。没有结果时，它返回同一个子工作流请求。

```rust
use a3s_flow::{WorkflowSpec, WorkflowTerminalOutcome};
use serde_json::json;

if let Some(outcome) = ctx.child_workflow_outcome("reserve-stock") {
    return match outcome {
        WorkflowTerminalOutcome::Completed { output } => {
            Ok(ctx.complete(output.clone()))
        }
        other => Ok(ctx.fail(format!("stock child ended with {other:?}"))),
    };
}

let spec = WorkflowSpec::rust_embedded(
    "inventory.reserve",
    "1.0.0",
    "workflows::inventory",
    "main",
);

Ok(ctx.start_child_workflow(
    "reserve-stock",
    spec,
    json!({ "sku": "A-1", "quantity": 2 }),
))
```

`ctx.child_workflow_run_id(child_id)` 可以读取引擎生成的根运行 ID。业务逻辑通常按 `child_id` 读取结果，日志与运维界面再使用全局运行 ID 定位子历史。

同一个 `child_id` 第二次出现时，引擎会比较 `spec`、`input` 和取消策略。任何一项变化都会产生非确定性错误。已经解析完成的子运行也不能作为唯一决定再次提交，工作流必须读取结果并向后推进。

## 父运行停止时的策略

`ChildWorkflowCancellationPolicy` 决定父运行停止时怎样处理仍在运行的子项。

| 值                     | 父运行行为                                   | 适用情况                                             |
| ---------------------- | -------------------------------------------- | ---------------------------------------------------- |
| `request_cancellation` | 向子运行写入清理式取消请求，并等待其持久终态 | 子工作流拥有需要释放的资源，或父运行必须知道清理结果 |
| `abandon`              | 解除等待，允许子运行独立继续                 | 子工作本来就能独立完成，父运行不再消费它的结果       |

父运行发出清理式取消后，引擎只把请求传播给取消之前已经打开、并使用 `request_cancellation` 的子运行。父运行会停在 `cancelling`，直到这些子运行结束。使用 `abandon` 的子运行不会阻止父运行终止。

父运行正常完成、失败或超时时，也不能越过仍然打开的 `request_cancellation` 子运行。这个检查防止父历史关闭后留下无人负责的子项。

## 子工作流批次 `StartChildWorkflows`

批次适合一组彼此独立、可以同时推进的子运行。命令接受 `Vec<ChildWorkflowCommand>`，成员数量为 1 到 64。每个成员拥有自己的 `child_id`、`spec`、`input` 与取消策略。

```rust
let children = items
    .iter()
    .enumerate()
    .map(|(index, item)| {
        ctx.child_workflow(
            format!("item-{index:04}"),
            item_spec.clone(),
            item.clone(),
        )
    })
    .collect();

Ok(ctx.start_child_workflows(children))
```

| 批次约束             | 引擎行为                                               |
| -------------------- | ------------------------------------------------------ |
| 成员不能为空         | 空批次返回 `InvalidTransition`                         |
| `child_id` 必须唯一  | 重复身份会在创建任何子运行前被拒绝                     |
| 成员不能超过 64 个   | 更大扇出需要按确定性窗口拆分                           |
| 声明顺序保持稳定     | 引擎按该顺序持久保存缺失请求                           |
| 已有成员必须形成前缀 | 历史中已有成员出现在缺失成员之后时，批次顺序被视为漂移 |

引擎会先校验整批定义，再追加所有缺失的 `ChildWorkflowRequested` 事件。完成这一步以后，它才并发协调子运行。这样可以避免前几个子项已经启动，后一个无效成员才使命令失败。

结果到达顺序没有业务含义。父工作流按稳定 `child_id` 聚合 `child_workflow_outcome()`，不能按哪个子项先完成来编号。64 个成员仍然过大时，可从输入中的确定性游标构造下一批，上一批全部到达终态后再推进游标。

## 续段 `ContinueAsNew`

续段把长历史切成几段独立的追加式事件流。当前段先写入 `RunContinuedAsNew`，其中包含引擎生成的后继运行 ID 与新输入。后继段继承当前 `WorkflowSpec` 的完整值，只有输入发生变化。

| 属性    | 类型 | 必填 | 规则                                     |
| ------- | ---- | ---- | ---------------------------------------- |
| `input` | JSON | 是   | 后继段的初始输入，通常包含游标和累计状态 |

```rust
let cursor = ctx.input()["cursor"].as_u64().unwrap_or(0);

if cursor >= 10_000 {
    return Ok(ctx.complete(json!({ "processed": cursor })));
}

if segment_finished {
    return Ok(ctx.continue_as_new(json!({
        "cursor": cursor + segment_size,
    })));
}
```

续段有几条明确边界。

- 当前运行处于 `cancelling` 时不能续段，清理路径只能返回 `cancel` 或 `fail`。
- 历史中还有未消费信号时不能续段，消息必须先配给等待节点。
- 后继段继承运行时构建身份、补丁标记与信号声明，命令不能顺便升级定义。
- `drive(root_run_id)` 会修复已提交但尚未创建的后继段，并返回当前活动叶子。
- 引擎默认最多跟随 64 次续段，可通过构建器显式调整上限。

调用方需要完整审计时使用 `continuation_chain(root_run_id)`。每个返回项都拥有自己的事件序号和终态，前一段的终态结果为 `continued_as_new`。

## `iteration` 与 `loop` 图容器

这两个名称属于 `WorkflowDag` 的结构约定。它们不会直接生成 `RuntimeCommand`，也没有内置的数组遍历、停止表达式或并发参数。宿主定义这些业务属性，并把发布后的图编译成步骤、等待或子工作流命令。

| 节点类型          | 必要结构                                            | 宿主通常补充的语义                     |
| ----------------- | --------------------------------------------------- | -------------------------------------- |
| `iteration`       | `data.start_node_id` 指向容器内的 `iteration-start` | 数据集合、成员变量、并发窗口与输出聚合 |
| `loop`            | `data.start_node_id` 指向容器内的 `loop-start`      | 继续条件、退出条件、最大次数与退避     |
| `iteration-start` | `parentId` 指向 `iteration`                         | 容器入口标记，不单独执行               |
| `loop-start`      | `parentId` 指向 `loop`                              | 容器入口标记，不单独执行               |

```json
{
  "nodes": [
    {
      "id": "for-each-item",
      "data": {
        "type": "iteration",
        "start_node_id": "iteration-start"
      }
    },
    {
      "id": "iteration-start",
      "parentId": "for-each-item",
      "data": { "type": "iteration-start" }
    },
    {
      "id": "process-item",
      "parentId": "for-each-item",
      "data": { "type": "service-call" }
    }
  ],
  "edges": [
    {
      "id": "iteration-start-process-item",
      "source": "iteration-start",
      "target": "process-item"
    }
  ]
}
```

每个容器至少还要有一个起始标记之外的子节点。`parentId` 只能指向存在的 `iteration` 或 `loop`。边的起点和终点必须位于同一作用域，顶层边不能直接连到容器内部。容器可以嵌套，整条 `parentId` 链不能形成环。

`execution_plan()` 分别为顶层和每个容器作用域计算拓扑顺序。任一作用域出现环路都会拒绝整张图。同一时刻就绪的节点按稳定 ID 排序，画布上的位置和节点数组顺序不会改变执行计划。

## 怎样选择

| 需求                                 | 选择                       |
| ------------------------------------ | -------------------------- |
| 一项工作需要独立历史、信号与终态     | 单个子工作流               |
| 一批独立工作要并发推进并由父运行收集 | 子工作流批次               |
| 同一执行长期运行，历史需要定期缩短   | 续段                       |
| 画布需要一块局部拓扑作用域           | `iteration` 或 `loop` 容器 |

图容器负责发布结构，子工作流负责运行生命周期。宿主可以把一个容器编译成多个稳定步骤，也可以为每个成员创建子工作流，选择取决于成员是否需要独立历史和外部控制。
