# Agent Skill

Flow 1.0 does not ship a standalone Agent Skill package or installer with the crate, native TypeScript compiler, or documentation. Flow does not discover, parse, or execute `SKILL.md`. A coding agent or host-owned agent runtime reads that file to learn how to change workflows, which checks to run, and where to stop when a risk is unresolved.

A project can still maintain its own Flow Skill. It can describe repository ownership, stable identity rules, replay safety, and release validation. The running Flow engine accepts `WorkflowSpec`, durable history, and `RuntimeCommand`; Skill content does not automatically enter any of those protocols.

## Two integration paths

| Path          | Reader                                    | Purpose                                                       | Flow's role                                 |
| ------------- | ----------------------------------------- | ------------------------------------------------------------- | ------------------------------------------- |
| Coding Skill  | Coding agent in a development environment | Create or edit workflow source and run replay-safe validation | Supply the library being changed and tested |
| Runtime Skill | Host-owned agent executor                 | Invoke a model, tool, or bounded task during a business run   | Persist one invocation as a durable step    |

A coding Skill belongs to repository development. A runtime Skill belongs to application execution. They may share business guidance, but permissions, inputs, and result protocols need separate definitions.

## Project-local layout

This is one clear project layout. The agent product decides its discovery directories; Flow has no path requirement.

```text
.agents/
└── skills/
    └── a3s-flow-workflows/
        ├── SKILL.md
        └── references/
            ├── replay-safety.md
            └── release-checklist.md
```

Commit `SKILL.md` beside the workflow conventions it describes. If an agent environment uses another discovery directory, preserve the content and adjust the outer path for that environment.

## Minimal `SKILL.md` template

The template below references capabilities already present in the repository. It does not claim that Flow installs or runs the file.

````markdown
---
name: a3s-flow-workflows
description: Create, review, and validate durable A3S Flow workflows in this repository.
---

# A3S Flow workflow development

Use this skill for changes to workflow replay code, durable steps, waits,
signals, hooks, child workflows, continuation, and native TypeScript sources.

## Before editing

1. Find the crate or application that owns the workflow.
2. Read its local AGENTS.md and existing workflow tests.
3. Identify every stable step, wait, hook, signal-wait, and child ID touched.
4. Confirm whether deployed histories must replay the changed path.

## Implementation rules

- Read durable history before returning a command.
- Derive identities from published input or deterministic indexes.
- Keep external effects inside registered step executors.
- Reuse exact command properties on replay.
- Use patch markers for replay-visible code changes.
- Do not put credentials, callback tokens, or large payloads in history.

## Validation

Run focused crate tests from the Flow crate workspace.

```sh
cargo fmt --all
cargo test -p a3s-flow
```

For native TypeScript changes, also verify the compiler contract.

```sh
a3s-flow-native-compiler capabilities
a3s-flow-native-compiler dependencies path/to/main.ts
```

## Handoff

Report changed stable IDs, patch markers, runtime build requirements, and the
exact commands that passed.
````

Narrow the commands to the repository. A large monorepo will usually replace `cargo test -p a3s-flow` with a package or integration test that covers the changed workflow. A useful Skill names an observable result; a vague instruction to ensure tests pass leaves the agent without a completion criterion.

## What a coding Skill should specify

| Topic             | Required guidance                                                                   |
| ----------------- | ----------------------------------------------------------------------------------- |
| Ownership         | Crate, application, or directory that owns workflow code and step executors         |
| Stable identities | Inputs or indexes used to derive IDs, including legacy IDs still present in history |
| Replay            | Fields that cannot change after commit and the patch-marker policy                  |
| External effects  | Registered `step_name`, idempotency-key construction, and side-effect owner         |
| Recovery          | Timer scan, task dispatch, hook resumption, and signal delivery responsibility      |
| Versioning        | `WorkflowSpec.version`, runtime build identity, and rollout order                   |
| Validation        | Exact test commands, required fixtures, and observable success conditions           |

A Skill can link to longer repository references while keeping its main file focused on decision order and mandatory constraints. Commit those references and link them by relative path, so the agent does not fetch a different version from the network.

## Wrap a runtime Skill in a durable step

When a business workflow needs agent execution, the host registers an ordinary step executor such as `agent.skill.run`. Flow owns durable identity, retry, and output. The host loads the Skill, starts the agent, restricts tools, and returns JSON.

```rust
if let Some(result) = ctx.step_output("review-order-1042") {
    return Ok(ctx.complete(result.clone()));
}

Ok(ctx.schedule_step_with_retry(
    "review-order-1042",
    "agent.skill.run",
    json!({
        "skill_id": "order-review",
        "skill_revision": "sha256:6f3d...",
        "instruction": "Review order ord-1042 against the stored policy",
        "artifact_refs": ["policy://orders/2026-08"],
        "allowed_tools": ["orders.read", "policy.read"]
    }),
    RetryPolicy::fixed(3, Duration::from_secs(5)),
))
```

The executor receives `StepInvocation` and performs host-owned work.

1. Resolve `skill_id` and its pinned revision through an allowlist.
2. Load trusted Skill content and referenced files.
3. Create an isolated execution environment with only admitted tools.
4. Derive an idempotency identity from `run_id` and `step_id`.
5. Validate and return a structured JSON result.

Agent output may vary across fresh invocations. The first successful output enters `StepCompleted`, and later workflow replay reads that durable value instead of invoking the agent again. A step retry can still repeat an external write, so the executor must pass the same idempotency identity into every mutating tool.

## Recommended step input

| Field            | Purpose                            | History rule                                          |
| ---------------- | ---------------------------------- | ----------------------------------------------------- |
| `skill_id`       | Select an allowed host Skill       | Use a stable logical name                             |
| `skill_revision` | Pin exact content                  | Use a commit, artifact version, or content digest     |
| `instruction`    | Describe the current business task | Keep it bounded and free of secrets                   |
| `artifact_refs`  | Reference immutable inputs         | Prefer references and digests to large history values |
| `allowed_tools`  | Narrow invocation authority        | Host intersects it with a server-side allowlist       |
| `result_schema`  | Constrain output                   | Host validates before returning the step result       |

Do not persist only `skill_id` and then read a mutable file by that name. A retry may occur after another deployment changed its content. A pinned revision or digest lets the executor load the same instructions, while runtime build identity keeps old histories on compatible code.

## Failure, cancellation, and timeout

When agent execution fails, the step executor returns a contextual error and lets `RetryPolicy` schedule another attempt. After exhaustion, the workflow can fail or use `continue_workflow` to enter a human hook or a safe fallback.

A cancellation request makes pre-existing pending work non-actionable. The executor must also react to host cancellation and lease loss by stopping its child processes and network requests. If cleanup genuinely needs an agent, use a fresh step ID and a smaller tool set.

Flow's `Timeout` command records a business deadline. The host executor owns the process limit for one agent invocation. They address different deadlines, so a step error should identify which limit fired.

## Security boundary

- Load Skill files from trusted, version-pinned artifacts.
- Let the host own the tool allowlist; Skill text cannot expand authority.
- Inject credentials through the execution environment, never command input or history.
- Give mutating tools an idempotency identity and independent audit record.
- Enforce result schema and size limits before Flow persists step output.
- Include Skill revision, agent runtime version, and tool protocol in deployment compatibility checks.

The current release has no official Skill installation command. Configure discovery for the project's agent environment and test that loading separately. Flow-side validation covers the wrapper step, replay equality, retries, and terminal behavior.

## Validation checklist

Before release, exercise a first invocation, replay of the same history, and a failed step retry. Verify that a missing Skill revision fails closed, a disallowed tool leaves a clear error, and cancellation reaps the agent child process. Finally, inspect history for only business input, stable references, and structured output, with no tokens, environment values, or complete model logs.
