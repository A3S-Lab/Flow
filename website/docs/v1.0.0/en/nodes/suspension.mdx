# Suspension and external input nodes

All three node types suspend a run and release its worker. The event store retains the condition. A scheduler or external caller later appends the satisfying event, and any compatible worker can continue replay.

## Timer wait `WaitUntil`

A timer wait persists one stable identity and an absolute UTC time. Use it for business deadlines, cooldown periods, polling intervals, and scheduled release outside step retry.

| Property    | Type            | Required | Rule                                                   |
| ----------- | --------------- | -------- | ------------------------------------------------------ |
| `wait_id`   | `String`        | Yes      | Stable in the run and reused for the same logical wait |
| `resume_at` | `DateTime<Utc>` | Yes      | Absolute UTC time that cannot change after creation    |

```rust
let wait_id = "payment-window";
let resume_at = ctx
    .input()["payment_deadline"]
    .as_str()
    .ok_or_else(|| FlowError::Runtime("missing payment_deadline".into()))?
    .parse::<DateTime<Utc>>()?;

if !ctx.wait_completed(wait_id) {
    return Ok(ctx.wait_until(wait_id, resume_at));
}
```

The first command appends `WaitCreated` and suspends. At the deadline, a host can call `resume_wait()`, scan due items with `FlowScheduler`, or dispatch targeted recovery through a task queue. Creating a wait whose deadline is already past still produces a durable record first. A recovery path must commit its completion.

Returning the same `wait_id` with a different `resume_at` yields `NonDeterministic`. A completed wait causes replay to continue, so workflow code should use `wait_completed()` and advance.

Cleanup-aware cancellation marks existing waits as cancelled. If cleanup needs a delay, use a new stable ID such as `cleanup-backoff-1`. Resubmitting a cancelled ID is rejected.

## Named signal `WaitForSignal`

Signals suit business input where one name may receive several messages, including inventory changes, human decisions, or device state. A signal enters history first, then pairs with a wait in receipt order.

### Workflow declaration

Declare every signal name in `WorkflowSpec` before creating the run.

```rust
let spec = WorkflowSpec::rust_embedded(
    "order.approval",
    "1.0.0",
    "workflows::order",
    "main",
)
.with_signal("order.approved")
.with_signal("order.rejected");
```

An undeclared name cannot be delivered or awaited. The declaration set belongs to the immutable run definition and cannot be extended in place.

### Wait properties

| Property      | Type     | Required | Rule                                                         |
| ------------- | -------- | -------- | ------------------------------------------------------------ |
| `wait_id`     | `String` | Yes      | Non-empty, with one distinct stable identity per consumption |
| `signal_name` | `String` | Yes      | Non-empty and declared in `WorkflowSpec`                     |

```rust
if let Some(payload) = ctx.signal_payload("approval-1") {
    return Ok(ctx.complete(payload.clone()));
}

Ok(ctx.wait_for_signal("approval-1", "order.approved"))
```

One wait consumes one message. Same-name waits are ordered by creation sequence. Same-name signals are ordered by receipt sequence. The oldest wait receives the oldest unconsumed signal. To read three messages, use deterministic IDs such as `approval-1`, `approval-2`, and `approval-3`.

### Delivery properties

External callers send a `WorkflowSignal` through `FlowEngine::send_signal()`.

| Property    | Type     | Required | Rule                                                         |
| ----------- | -------- | -------- | ------------------------------------------------------------ |
| `signal_id` | `String` | Yes      | Caller-owned idempotency identity, reused unchanged on retry |
| `name`      | `String` | Yes      | Declared signal contract name                                |
| `payload`   | JSON     | Yes      | Complete business payload stored in durable history          |

```rust
let signal = WorkflowSignal::new(
    "approval-delivery-8421",
    "order.approved",
    json!({ "approved_by": "manager-17" }),
);

let snapshot = engine.send_signal(&run_id, signal).await?;
```

A redelivery with the same target run and `signal_id` must preserve name and payload. Drift returns `SignalConflict`. When delivery targets the root of a continuation chain, the engine locates the active leaf and checks the entire chain for an earlier copy of that `signal_id`.

A terminal run cannot receive a new signal. A persisted but unconsumed signal also blocks `continue_as_new()` so a message cannot disappear at a segment boundary.

## External hook `CreateHook`

Use a hook when one external request needs a public token, audit metadata, and explicit received or disposed state. Approval links, webhook callbacks, and one-time human input commonly use hooks.

| Property   | Type     | Required | Rule                                                                  |
| ---------- | -------- | -------- | --------------------------------------------------------------------- |
| `hook_id`  | `String` | Yes      | Stable identity inside the run                                        |
| `token`    | `String` | Yes      | Bearer value used for routing and unique among active hooks           |
| `metadata` | JSON     | No       | Audit and host routing information, defaulting to an empty JSON value |

```rust
let hook_id = "manager-approval";

if let Some(payload) = ctx.hook_payload(hook_id) {
    return Ok(ctx.complete(payload.clone()));
}
if ctx.hook_disposed(hook_id) {
    return Ok(ctx.fail("approval was withdrawn"));
}

let metadata = HookMetadata::human_approval("Approve order ord-1042")
    .with_callback_route(HookCallbackRoute::post("/callbacks/flow/hooks"))
    .with_label("tenant", "acme")
    .with_data("order_id", json!("ord-1042"));

Ok(ctx.create_hook_with_metadata(
    hook_id,
    "opaque-public-token",
    metadata,
)?)
```

`HookMetadata` provides optional standard fields.

| Field             | Type             | Purpose                                     |
| ----------------- | ---------------- | ------------------------------------------- |
| `kind`            | `String`         | Application-defined routing and audit class |
| `subject`         | `Option<String>` | Human-readable subject                      |
| `callback.method` | `String`         | Uppercase HTTP method                       |
| `callback.path`   | `String`         | Public path owned by the host               |
| `labels`          | String map       | Small searchable labels                     |
| `data`            | JSON map         | Structured application metadata             |

These fields enter history and do not create an HTTP route. The host authenticates callback requests, resolves active hooks from tokens, and bounds payload size.

### Receipt and disposal

| API                                     | Use                                    | Redelivery rule                           |
| --------------------------------------- | -------------------------------------- | ----------------------------------------- |
| `resume_hook(run_id, hook_id, payload)` | Caller retained stable identities      | Matching receipt can be retried reliably  |
| `resume_hook_by_token(token, payload)`  | First call knows only the public token | Searches active hooks only                |
| `dispose_hook(run_id, hook_id)`         | Dispose by stable identity             | Matching disposal can be retried reliably |
| `dispose_hook_by_token(token)`          | First disposal knows only the token    | Searches active hooks only                |

After a token resolves successfully, store the returned run ID and hook ID. Once a hook is received or disposed, the active-token index no longer returns it. Stable-identity methods can still compare a retry with durable history.

One hook cannot be received and disposed. A changed receipt payload, token, or metadata produces an explicit conflict. Error `Display` and `Debug` redact tokens, and application logs should avoid printing them independently.

A cancellation request closes current active hooks. A cleanup path that needs another external confirmation must use a new hook ID and token.

## Signal or hook

| Situation                                          | Choose     |
| -------------------------------------------------- | ---------- |
| One name receives a queue of messages              | Signal     |
| Each message has caller-owned idempotency identity | Signal     |
| One request needs a public bearer token            | Hook       |
| The request needs received and disposed states     | Hook       |
| Only a fixed time matters                          | Timer wait |

None of these nodes occupies a sleeping worker. Production deployment still needs recovery scanning, targeted task dispatch, and active-hook indexes. An event store alone cannot advance suspended work automatically.
