# Node catalog

Flow 1.0 handles nodes at two layers. `WorkflowDagNode` stores an authoring-graph node. `RuntimeCommand` states the next durable decision the engine must commit. A host compiler may turn one graph node into one or several runtime commands. The two objects are not interchangeable.

## Node configuration example

The embedded configurator covers all 14 durable commands and both structural containers. Fields are grouped by identity, input, retry, and terminal conditions. Dependent controls appear as their governing policy changes. The page keeps a draft for every selected node and places validation beside the responsible field. Step and child batches support member insertion and removal, and JSON can be copied only after validation passes.

On desktop, the node catalog sits beside a full-width form and the JSON preview follows the form, preserving useful field widths. Mobile turns the node catalog into a horizontal selector and collapses fields to one column. Category tabs support arrow keys, `Home`, and `End`, and every control remains keyboard accessible. The configurator explains the contract on this page; it does not create or save a workflow.

## Supported boundary

| Layer           | What Flow 1.0 accepts                                    | What Flow validates                                                                 | What the host still owns                                             |
| --------------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Graph node      | Any non-empty string in `data.type`                      | Identity, edges, scopes, cycles, and stable order                                   | Property schemas, authorization, and executors                       |
| Container node  | `iteration`, `loop`, `iteration-start`, and `loop-start` | Parent relationships, start nodes, and scoped edges                                 | Iteration data, stop conditions, concurrency, and output aggregation |
| Runtime command | 14 `RuntimeCommand` variants                             | History events, replay equality, suspension, terminal state, and concurrent appends | External effects, credentials, tenancy, and logical idempotency      |

Names such as `start`, `end`, `llm`, `code`, and `tool` may appear in `data.type`. Structural compilation does not attach an executor or infer a property schema for those names. A host must maintain an allowlist and versioned schemas, then compile admitted nodes into the durable commands below.

## The 14 durable commands

| Node purpose            | Rust constructor          | JSON `type`             | Result                                                    |
| ----------------------- | ------------------------- | ----------------------- | --------------------------------------------------------- |
| Single step             | `schedule_step()`         | `schedule_step`         | Run one host step and persist its output                  |
| Step batch              | `schedule_steps()`        | `schedule_steps`        | Persist every identity, then advance members concurrently |
| Progress                | `record_progress()`       | `record_progress`       | Append one update with a stable ID                        |
| External operation link | `link_child_operation()`  | `link_child_operation`  | Persist a reference managed by another owner              |
| Timer wait              | `wait_until()`            | `wait_until`            | Suspend until a UTC deadline                              |
| Signal wait             | `wait_for_signal()`       | `wait_for_signal`       | Consume the oldest unused signal with one name            |
| External hook           | `create_hook()`           | `create_hook`           | Wait for token-routed receipt or disposal                 |
| Single child workflow   | `start_child_workflow()`  | `start_child_workflow`  | Start or await one first-class child run                  |
| Child workflow batch    | `start_child_workflows()` | `start_child_workflows` | Durably declare up to 64 child runs                       |
| Continuation            | `continue_as_new()`       | `continue_as_new`       | Close one history and create its successor                |
| Success                 | `complete()`              | `complete`              | Commit a successful terminal output                       |
| Failure                 | `fail()`                  | `fail`                  | Commit an application failure                             |
| Finish cancellation     | `cancel()`                | `cancel`                | Finish an existing cleanup-aware cancellation             |
| Timeout                 | `timeout()`               | `timeout`               | Commit a deadline and optional reason                     |

Each `run_workflow()` call returns exactly one command. The engine commits resulting events and invokes workflow code again against the new history. A batch command is still one decision, while the engine persists and advances its members under their individual identities.

## Common graph-node properties

```json
{
  "id": "charge-order",
  "type": "custom",
  "position": { "x": 320, "y": 120 },
  "data": {
    "type": "service-call",
    "operation": "billing.charge",
    "retry_profile": "payment"
  }
}
```

| Property               | Required | Execution meaning                                                                            |
| ---------------------- | -------- | -------------------------------------------------------------------------------------------- |
| `id`                   | Yes      | Stable graph identity, non-empty and unique                                                  |
| `data`                 | Yes      | Complete semantic object included in the execution digest                                    |
| `data.type`            | Yes      | Non-empty discriminator used by the host to select a schema and executor                     |
| `parentId`             | No       | Container identity, limited to an `iteration` or `loop` parent                               |
| Other top-level fields | No       | Losslessly preserved presentation data such as `type`, `position`, dimensions, and selection |

Presentation fields do not change `execution_digest()`. Node `data`, `parentId`, edge endpoints, and semantic edge data do change it. Source array order does not affect the plan either. Nodes that are simultaneously ready within a scope are ordered by stable ID.

## Common edge properties

| Property               | Required | Meaning                                                     |
| ---------------------- | -------- | ----------------------------------------------------------- |
| `id`                   | Yes      | Unique, non-empty graph identity                            |
| `source`               | Yes      | Existing source node ID                                     |
| `target`               | Yes      | Existing target node ID                                     |
| `sourceHandle`         | No       | Source connector in the authoring canvas                    |
| `targetHandle`         | No       | Target connector in the authoring canvas                    |
| `data`                 | No       | Branch label or other host semantics included in the digest |
| Other top-level fields | No       | Losslessly preserved presentation data                      |

An edge cannot connect a node to itself or cross between the top level and a container scope. A cycle in any scope makes `execution_plan()` fail.

## Compiling a graph node into a durable command

The mapping below belongs to an example host. `service-call` is that host's node type and is not registered by Flow.

```rust
match node.node_type() {
    "service-call" => {
        let operation = node.data()["operation"]
            .as_str()
            .ok_or_else(|| FlowError::Runtime("missing operation".into()))?;

        Ok(ctx.schedule_step(
            format!("node:{}", node.id()),
            operation,
            resolved_input,
        ))
    }
    node_type => Err(FlowError::Runtime(
        format!("unsupported node type {node_type}"),
    )),
}
```

Before publication, validate properties, resolve variables, check authority, and pin executor versions. During a run, load only the published graph and bindings. A changed canvas cannot reinterpret existing history.

## Identity rules

Derive stable IDs from the published graph or deterministic indexes. Do not generate UUIDs, read the current clock, or number nodes by completion order inside replay code. After the first commit, step names, inputs, retry policies, wait deadlines, signal names, hook tokens, child definitions, and cancellation policies belong to history. Returning the same ID with changed properties produces a non-determinism error.
